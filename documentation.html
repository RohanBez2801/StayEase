Coursework Documentation

Grade 11 Computer Science Project Description & Test Plan.

1. Description of the Problem

Shipiki Hotels is a small guest-house chain currently relying on an outdated system of telephone calls, walk-in bookings, paper diaries, wall charts, and printed price lists. This manual approach leads to double-bookings, errors in manual price calculation, poor visibility of room availability across different branches, and weak reporting capabilities.

2. Specific Objectives

To develop a browser-based online prototype that solves the problems of double-booking, automates price calculations (including tax and discounts), improves room availability visibility through a search feature, and provides basic reporting for staff.

3. Description and Evaluation of Existing Solution

The current manual process (paper diaries and wall charts) is highly error-prone and time-consuming. It offers no automatic overlap detection, leading to overbooking. It is completely manual, making revenue tracking and occupancy reporting difficult and inaccurate.

4. Other Possible Solutions

Other solutions include purchasing an expensive, off-the-shelf enterprise Hotel Management System or subscribing to a cloud-based SaaS platform. However, these are often too complex and costly for a small guest-house chain like Shipiki Hotels.

5. Overall Plan

The plan is to create a digital prototype of an Online Hotel Reservation and Booking Management System. The prototype will be built using HTML, CSS, and vanilla JavaScript, utilizing localStorage for data persistence to demonstrate core functionality without requiring a backend server or database.

6. Separate Modules

  • Room Management: Managing room details, prices, capacities, and branch locations.
  • Guest Management: Storing guest contact information.
  • Booking Engine: Searching for available rooms, calculating costs, and preventing date overlaps.
  • Dashboard & Reporting: Providing a summary of key metrics and a timeline view of upcoming check-ins.

7. Method of Solution

The solution uses modular JavaScript files (data.js, rooms.js, guests.js, bookings.js, reports.js) to separate concerns. It employs robust date logic to prevent double-booking, and mathematical formulas to automatically calculate subtotals, a 10% discount for stays longer than 3 nights, and a 15% tax rate.

8. Hardware and Software Requirements

Hardware: Any standard desktop or laptop computer.
Software: A modern web browser (e.g., Google Chrome, Mozilla Firefox, Microsoft Edge, Safari) with JavaScript enabled. No additional servers or databases are required for this prototype.

9. Programming Code

The codebase utilizes vanilla JavaScript (ES5/ES6) for DOM manipulation and business logic. CSS is used for responsive styling (flexbox and grid). Data is serialized to JSON strings and stored in the browser's localStorage.

10. Test Strategy

The system is tested using User Acceptance Testing (UAT) with a focus on normal, boundary, and erroneous data inputs to ensure robustness.

12. Technical Documentation

The architecture relies entirely on the client-side. localStorage is used as a mock database. The stayease_rooms, stayease_guests, and stayease_bookings keys store the serialized JSON data. Functions like hasDateOverlap() in utils.js handle the core validation logic.

13. User Documentation

To use the system, open index.html in a web browser. Use the sidebar to navigate between Dashboard, Rooms, Guests, Bookings, and Reports. Create rooms and guests first before attempting to make a booking. Use the "Search Availability" button on the Bookings page to find rooms for a specific branch.

14. Evaluation

The prototype successfully meets the core objectives of preventing double bookings and automating calculations. It provides a massive improvement over the old paper-based system by centralizing data and offering instant reporting.

15. Opportunities for System Development

  • Migrate data storage from localStorage to an actual backend database (like Firebase or MySQL).
  • Implement user authentication (Login page for staff vs managers).
  • Integrate a real payment gateway (e.g., PayFast or Stripe).
  • Add automated email confirmations via an SMTP server.

16. Prototype Limitations

Important Notice: This is a Grade 11 coursework prototype.
  • Data is stored only in the current browser using localStorage. It will be lost if browser data is cleared.
  • It is a single-user demonstration, not a live multi-user system (no simultaneous multi-user locking).
  • Payment processing and email confirmations are simulated only. No real transactions take place.
  • Login/security features and password encryption are not implemented in this prototype.
  • A production version would require a secure server, database, authentication, payment gateway, and email service.
